# User Guide

This guide walks through installing, customizing, and operating the aw-pack workflows in your GitHub repository.

## Quick Start

Three commands to go from zero to a fully automated repository:

```bash
gh extension install github/gh-aw          # install the gh-aw CLI (one-time)
gh aw add "srdjan/aw-pack/*"               # install all 5 workflows
gh aw secrets set ANTHROPIC_API_KEY         # set your API key
```

Commit the generated files and push. The workflows activate on their respective triggers immediately.

## What Gets Installed

After running `gh aw add`, your repository will have:

```
.github/
  aw/
    actions-lock.json                # SHA-pinned action dependencies
    imports/                         # cached shared imports
  workflows/
    shared/
      repo-context.md               # your project context (edit this)
    issue-triage.md                  # source workflow
    issue-triage.lock.yml            # compiled GitHub Actions YAML
    pr-review.md
    pr-review.lock.yml
    doc-sync.md
    doc-sync.lock.yml
    weekly-status.md
    weekly-status.lock.yml
    repo-assist.md
    repo-assist.lock.yml
.gitattributes                       # marks .lock.yml as generated
```

The `.md` files are your editable source. The `.lock.yml` files are generated by `gh aw compile` and should never be edited directly. Both must be committed to version control.

## Understanding the Workflows

### Issue Triage

**Trigger**: whenever an issue is opened or reopened.

The agent reads the issue title and body, examines the codebase for context, and applies labels. It posts a short comment explaining its reasoning and pointing to relevant source files. It skips issues that are already labeled, assigned, or created by bots.

**Labels it can apply**: bug, enhancement, question, documentation, good-first-issue, help-wanted, security, performance.

**Rate limits**: 1 comment and 4 labels per run.

### PR Review

**Trigger**: whenever a pull request is opened or updated.

The agent reads all changed files, runs the project's build and test commands, and reviews the code against the project's conventions. It submits an APPROVE, REQUEST_CHANGES, or COMMENT review depending on what it finds. It flags breaking changes to public APIs.

**What it runs**: it discovers your build/test commands from package.json, Makefile, deno.json, Cargo.toml, etc. The bash allowlist covers npm, yarn, pnpm, deno, cargo, pytest, go, ruby, and make.

**Rate limits**: 1 review, 1 comment, and 3 labels per run.

### Weekly Status

**Trigger**: every Monday (fuzzy schedule) and on-demand via `workflow_dispatch`.

Creates a GitHub issue summarizing the past 7 days of activity: issues opened/closed, PRs merged/open, commits grouped by category, and a breaking change watch. The most important section is "Suggested Actions for Maintainer" with specific, checkbox-based action items.

Skips report creation entirely if there was zero activity.

**Rate limits**: 1 issue per run.

### Documentation Sync

**Trigger**: any push to the main branch.

Compares source code changes against documentation files (README.md, CLAUDE.md, CONTRIBUTING.md, ARCHITECTURE.md, and API docs). If documentation is stale, opens a draft PR with targeted fixes. If documentation is already consistent, does nothing.

**Rate limits**: 1 draft PR per run.

### Repo Assist

**Trigger**: daily schedule, on-demand via `workflow_dispatch`, and `/repo-assist` slash commands in issue comments.

This is the general-purpose assistant. It handles five maintenance tasks in round-robin rotation, picking the 2-3 highest priority ones each run:

1. **Stale PR nudging** - politely asks authors about PRs with no activity for 14+ days
2. **Welcome new contributors** - greets first-time contributors and points them to contributing guides
3. **CI failure diagnosis** - analyzes failing workflow runs, creates draft fix PRs for simple issues
4. **Label hygiene** - backfills labels on unlabeled items older than 24 hours
5. **Stale issue cleanup** - flags issues inactive for 30+ days with no assignee

It uses persistent repo-memory to track what it has done across runs, avoiding duplicate welcomes and repeated nudges.

**Slash commands**: comment `/repo-assist <instructions>` on any issue to trigger an on-demand run. Examples:
- `/repo-assist summarize this issue and suggest next steps`
- `/repo-assist check if this is a duplicate of another issue`
- `/repo-assist suggest which files need to change for this feature`

**Rate limits**: 6 comments, 2 draft PRs, 15 label additions, 1 issue creation per run.

## Customizing for Your Project

### The repo-context file

The single most impactful customization is editing `.github/workflows/shared/repo-context.md`. This file is imported by all five workflows and tells the agent about your project. It has four sections:

**Project**: your project name, a one-line description, the language/runtime, and the package identifier.

```markdown
## Project

Acme API is a REST service for widget management, written in Go. Module: github.com/acme/api.
```

**Architecture**: your project's modules, layers, or components with their source file paths. This is what the agent uses to categorize issues and PRs.

```markdown
## Architecture

- **Handlers**: `internal/handlers/` - HTTP request handlers
- **Services**: `internal/services/` - business logic
- **Models**: `internal/models/` - data structures and database models
- **Middleware**: `internal/middleware/` - auth, logging, rate limiting
- **Migrations**: `db/migrations/` - database schema changes
- **Config**: `config/` - environment and feature flag configuration
```

**Component Labels**: project-specific labels that map to your architecture. These go beyond the generic set (bug, enhancement, etc.) and let the agent tag issues by subsystem.

```markdown
## Component Labels

handlers, services, models, middleware, migrations, config
```

**Conventions and Build Commands**: your coding standards and the exact commands to build, test, and lint. This is what the PR reviewer enforces.

```markdown
## Conventions and Build Commands

Conventions:
- All exported functions must have godoc comments
- Error wrapping with fmt.Errorf and %w
- Table-driven tests with t.Run subtests
- No global state; pass dependencies via function arguments

Build: go build ./...
Test: go test ./...
Lint: golangci-lint run
Vet: go vet ./...
```

Without customization, the agent discovers this context at runtime by reading your README, package files, and configuration. Customization makes it faster and more consistent.

### Adding custom labels to the allowlist

The `safe-outputs` section in each workflow YAML frontmatter defines which labels the agent is allowed to apply. If you add component labels in your repo-context file, you also need to add them to the YAML allowlist in the relevant workflows.

For example, if your repo-context defines components `handlers`, `services`, `models`:

In `issue-triage.md`, find the `safe-outputs.add-labels.allowed` list and add your labels:

```yaml
safe-outputs:
  add-labels:
    max: 4
    allowed:
      - bug
      - enhancement
      - question
      - documentation
      - good-first-issue
      - help-wanted
      - security
      - performance
      - handlers        # added
      - services        # added
      - models          # added
```

Do the same for `repo-assist.md` (which also applies labels).

After editing, run `gh aw compile` to regenerate the lock files.

### Trimming the bash allowlist

The PR review, doc sync, and repo assist workflows include build/test commands for every major ecosystem. After installation, you can trim this to just your stack. For a Go project:

```yaml
tools:
  bash:
    - "go test ./..."
    - "go vet ./..."
    - "go build ./..."
    - "golangci-lint run"
```

### Changing the AI engine

All workflows default to Claude. To switch engines, edit the `engine:` field in each workflow's frontmatter:

```yaml
engine: copilot   # GitHub Copilot
engine: codex     # OpenAI Codex
engine: gemini    # Google Gemini
```

Then set the corresponding secret:

```bash
gh aw secrets bootstrap --engine copilot
```

## Day-to-Day Operations

### Running a workflow manually

```bash
gh aw run repo-assist           # trigger repo-assist immediately
gh aw run weekly-status         # generate a status report now
```

### Checking workflow status

```bash
gh aw status                    # show all workflows with last run info
gh aw logs repo-assist          # download and view recent run logs
gh aw health repo-assist        # show success rate metrics
```

### Testing without affecting your repo

```bash
gh aw trial repo-assist         # run in a temporary repo clone
```

### Enabling and disabling

```bash
gh aw disable weekly-status     # pause the weekly report
gh aw enable weekly-status      # resume it
```

### Receiving upstream updates

When the aw-pack gets improvements:

```bash
gh aw update                    # update all workflows
gh aw update repo-assist        # update one workflow
```

The update performs a 3-way merge between the version you originally installed, the new upstream version, and your local customizations. Your edits to repo-context, label lists, and bash commands are preserved. If there are conflicts, resolve them manually and run `gh aw compile`.

To overwrite local changes entirely:

```bash
gh aw update repo-assist --no-merge
```

## Security Model

The workflows implement defense-in-depth:

**Read-only agent**: the AI agent runs with read-only permissions. It cannot directly modify your repository, create issues, post comments, or push code.

**Safe-outputs**: every write operation goes through a separate, validated job with scoped permissions. The agent produces structured output requests that are executed by GitHub Actions jobs outside the agent's container.

**Rate limits**: every safe-output has a `max` cap. Even if the agent tries to create 100 comments, only the configured maximum (e.g., 6) will execute.

**Bash allowlist**: only explicitly listed commands can run. The agent cannot execute arbitrary shell commands.

**Draft PRs**: all PRs created by repo-assist and doc-sync are drafts by default. A maintainer must review and approve before merging.

**Bot disclosure**: every public comment begins with an automated notice so contributors know they are interacting with an AI.

**Sandboxed execution**: the agent runs in a containerized environment with network isolation. Only explicitly allowlisted domains are accessible.

## Troubleshooting

**Workflow not triggering**: verify the `.lock.yml` file is committed and pushed. Run `gh aw status` to check if the workflow is enabled.

**Compilation errors**: run `gh aw compile --validate` for detailed JSON schema validation. Common issues are invalid label names in safe-outputs or unrecognized toolset names.

**Agent not finding project context**: edit `shared/repo-context.md` with explicit project details rather than relying on runtime discovery. The agent is more reliable with explicit context.

**Too many comments/labels**: reduce the `max` values in the safe-outputs section of the relevant workflow.

**Wrong build commands running**: trim the bash allowlist to only your project's commands.

**Stale lock files after editing**: always run `gh aw compile` after editing any `.md` workflow file.
